### Cross-cutting concerns — which existing module owns them

- **Logging** → `tracing` crate (not module-scoped; the orchestrator does not own a logger).
- **Error context** → `thiserror` per-crate enums (`RuntimeError` in `runtime/mod.rs`, `CImageError` in `cimage/mod.rs`, `WorldError` in `prism-ecs-core/src/world.rs`).
- **Metrics** → none — there is no metrics module. If metrics are added later, they will live in a single `prism_observability` crate.
- **Retry** → none — dispatch helpers do not retry. The runtime is single-shot per `run_*` call.
- **Validation** → `validate_aot_schedule` (in `runtime/unified/replay.rs`) and `load_with_promotion` (in `runtime/model.rs`).
- **ID generation** → `uuid::Uuid::new_v4()` for ANE dispatch temp paths (in `runtime/unified/ane.rs`).
- **Type conversion** → `decode_f32_output` (in `runtime/mod.rs`), `decode_dispatch_tokens` + `decode_tensor_payload` (in `runtime/unified/dispatch.rs`).

There is no `helpers.rs`, `common.rs`, `utils.rs`, `misc.rs`, or `shared.rs` file introduced by this work.

### Propagation chain

N/A for this work. None of the four changes are state-bearing:

- The `world.rs` pilot is a pure API surface update (`spawn` now returns `Result<_, WorldError>`). The actual canonical state mutations still happen through the same `WorldTxn` boundary; the change does not add a new durable event, projection, or consumer.
- The `cimage/` decomposition is a pure file reorganization. The `.cimage` file format is byte-for-byte unchanged; the reader and writer still produce/parse the same bytes; no new event store or projection is touched.
- The `runtime/` decomposition (entity kind) and the `unified/` decomposition (responsibility) are both pure file reorganizations. The `UnifiedRuntime` public API is preserved; no new command, event, or projection is introduced.

The skill's propagation gate (`references/review-gates.md`) is therefore not invoked by this work. If a follow-up PR adds a new event or projection, that follow-up must name its chain (durable event → event store → replay applier → projection rebuild → read path → consumer) and ship a propagation test.

### Dependency order between new submodules

The new submodules have no inter-dependencies. Each holds an `impl
RuntimeModel` block for a different category of accessor. The parent
`runtime/model.rs` keeps the struct + the load functions + the read
helper. The submodules `use super::RuntimeModel;` to add the impl
blocks. Order of creation (no compile-time dependency between them):

1. `tensor_accessors.rs` (no deps on siblings)
2. `kernel_accessors.rs` (no deps on siblings)
3. `uop_accessors.rs` (no deps on siblings)
4. `evidence_accessors.rs` (no deps on siblings)
5. `registry_accessors.rs` (no deps on siblings)
6. `auxiliary.rs` (no deps on siblings)

After all six are created, the parent `model.rs` re-exports their
public surface (so `runtime::RuntimeModel::method` continues to work)
and removes the moved methods from its own `impl` block.
